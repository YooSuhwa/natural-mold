# 도구 거버넌스 상세 기획 (승인 기본값, 회사 제한, 등록, 공개 범위)

- 상태: **v1 초안**, 2026-11-10. 5장 결정 질문 G1~G14에 추천안을 적었고 사용자 확인을 기다린다. 구현은 확인 뒤 시작한다.
- 범위: 도구를 **누가 등록하고, 누가 보고 쓰며, 실행 전에 묻는지**를 한 틀로 정한다. 도구 자체의 승인 기본값, 회사의 도구별 기본값·허용 단계·잠금,
  등록 권한과 등록 승인, 사람·팀 지정. 지금은 도구(MCP 서버·MCP 도구·등록 도구)에 적용하고, 같은 틀을 스킬·하위 에이전트·A2A에 그대로 쓸 수 있게 설계한다.
- 순서: 지식 검색(순번 12)보다 먼저 끝낸다(사용자 지시, 2026-11-10). 지식 도구가 MCP 한 길로 붙기 때문에 이 규칙이 그 바닥이 된다.
- 앞선 문서: `approval-modes-plan.md`(도구 승인 모드, 1단계 구현됨). 이 문서는 그 판정 함수에 계층을 더하고, 그 문서가 다루지 않은 등록·공개 범위를 더한다.
- 근거: 사용자 요구(1.1), 현재 코드 조사(2장, `main` a19b6e01), 다른 플랫폼 조사(부록 A, 2026-11-10).

## 1. 목표와 완료 기준

### 1.1 사용자가 원한 모양

1. 도구마다 승인 설정이 3단계로 있다. **도구 설정에서 기본값**을 정하고, 에이전트에 붙이는 사람이 그 에이전트에서 바꿀 수 있다.
2. 회사는 도구마다 기본값을 정할 수 있고, **못 바꾸게 강제**할 수 있고, 3단계 중 **특정 단계를 못 쓰게** 할 수 있다.
3. 지식 도구는 기본이 읽기 전용(묻지 않음)이고 원하면 바꿀 수 있다. 회사든 개인이든 같다.
4. 회사는 **관리자만 도구를 등록**하게 하거나 **직원도 등록**하게 할 수 있다. 직원 등록은 **관리자 승인 뒤**에 쓰이게 하거나 바로 쓰이게 할 수 있다.
5. 직원이 등록한 것은 그 직원만 보고 쓰게 할 수 있다. 회사가 등록한 것은 **사람이나 팀을 지정**하고, 지정받지 않은 사람에게는 보이지 않는다.
6. 나중에 스킬, A2A, 에이전트도 같은 모양이 된다.

### 1.2 용어

- **승인 단계**: `always`(항상 묻기), `when`(조건에 맞을 때만 묻기), `never`(묻지 않기). 지금 에이전트 도구별 설정에 이미 있는 세 값이다
  (`backend/app/agent_runtime/runtime_policy.py:81-95`). 값을 두지 않으면 위 계층을 따른다.
- **사용 금지**: 승인 단계와 별개다. 도구가 목록·실행에서 사라진다.
- **리소스**: 에이전트에 붙여 쓰는 것. 지금은 MCP 서버, MCP 도구, 등록 도구. 뒤에 스킬, 하위 에이전트, A2A 원격 에이전트.

### 1.3 완료 기준

1. 도구(또는 MCP 서버) 설정에서 승인 기본값을 정하면, 그 도구를 붙인 모든 에이전트가 따로 바꾸지 않는 한 그 값으로 실행된다.
2. 회사 관리자가 도구마다 기본값과 허용 단계를 정하면, 허용되지 않은 단계는 저장과 실행 모두에서 거부되고 화면에 잠겨 보이며 이유가 표시된다.
3. 허용 단계를 하나만 남기면 그 값으로 고정된다(강제). `never` 하나만 남기는 것도 된다(지금은 "항상 묻기" 고정만 된다).
4. 같은 이름의 도구가 두 서버에 있어도 설정이 각각 정확히 적용된다(지금은 조용히 빠진다, 2.2).
5. 회사가 "등록 가능한 사람"을 리소스 종류마다 정하면, 권한 모드(legacy/enforce)와 상관없이 그대로 지켜진다.
6. 등록 승인을 켠 회사에서 직원이 등록한 도구는 관리자가 승인함에서 승인하기 전까지 어떤 에이전트에도 붙지 않고 실행되지 않는다.
7. 승인된 서버의 주소·실행 명령이 바뀌거나 도구 정의가 바뀌면 다시 승인을 받는다.
8. 회사가 등록한 도구를 사람·팀에 지정하면, 지정받지 않은 사람은 목록·선택기·실행 어디서도 그 도구를 보지 못한다.
9. "실제 적용" 표와 승인 카드, 감사 기록에 어느 계층이 결과를 정했는지가 남는다.
10. 스킬과 하위 에이전트에 같은 설정이 같은 판정 함수로 적용된다(6단계). A2A는 이 문서의 계약만 정하고 구현하지 않는다.

### 2.2 승인 판정

- 판정은 `decide` 한 곳(`tool_modes.py:79-116`). 순서: 회사 `block` → 숨김, 회사 `always_ask` → 묻기, 회사 등급 `approval` → 묻기,
  에이전트 도구별 설정, 옛 `human_in_the_loop` 설정, 대화 허용, 경로 모드 `auto`, 마지막에 위험 등급 기본값.
- 푸는 계층(도구별·대화 허용·경로 모드)은 **루트 에이전트에만** 적용된다. 하위 에이전트에는 회사 계층만 간다
  (`backend/app/agent_runtime/deep_agent_factory.py:344-354`, `tool_risk.py:243-275`).
- **설정 키가 도구 이름이다.** 에이전트 설정 `tools[name]`(`runtime_policy.py:105-108`), 회사 `always_ask`(`tool_modes.py:94`) 모두 문자열 일치.
  화면이 쓰는 이름은 MCP면 서버 접두사 없는 `mcp_tool_name`(`backend/app/approvals/tool_grants.py:38-49`).
- **이름 충돌 결함.** 두 서버가 같은 이름의 도구를 내면 실행 때 이름이 `srv_<해시>_<이름>`으로 바뀐다
  (`backend/app/agent_runtime/mcp_strict_loader.py:55-76`, 옛 로더는 `mcp_tool_loader.py:263-275`). 저장된 키(원래 이름)와 맞지 않아
  도구별 설정과 회사 "항상 묻기"가 **조용히 적용되지 않는다**. 등록 도구와 MCP 도구의 이름 충돌은 구분하지도 않는다.
- 회사 "항상 묻기" 목록은 화면에서 자유 입력 문자열이다(`frontend/src/features/guardrails/components/guardrail-tool-risk-form.tsx:35-57`).
- 실행별 고정: 회사 등급 동작과 `always_ask_tools`는 실행 행에 스냅숏으로 남아 재개 때 같은 답을 낸다(`backend/app/guardrails/pinning.py:1-8`).
- 예약 실행: `trigger_safe=False`인 도구는 예약에서 막힌다(`risk.py:311-327`, `backend/app/services/chat/trigger_blocked_tools.py`).
  MCP 도구는 신뢰 호스트가 아니면 항상 `False`다.

### 2.3 등록 권한

- 능력(cap) 7개: `cap_create_agent`, `cap_create_skill`, `cap_create_tool`, `cap_register_mcp`, `cap_publish_marketplace`는 builder 역할 이상이거나
  사람·그룹·조직 전체에 개별 부여. `cap_connect_database`, `cap_share_org_wide`는 admin 이상이거나 사람·그룹에 부여(`model.fga:32-38`).
- DB 쪽 같은 내용: 역할별 능력과 개별 부여 표 `OrgCapabilityGrant`(`backend/app/authz/org_permissions.py:14-25,76-80`,
  `backend/app/models/organization_group.py:82`). 일반 구성원은 부여받지 않으면 능력이 없다. 조직을 만들 때 부여 행을 넣는 코드는 없다.
- 관리 API·화면: `GET/PUT /api/orgs/{org_id}/capabilities`(`backend/app/routers/org_assignments.py:57-86`),
  `frontend/src/app/settings/organization/roles/page.tsx`.
- **legacy에서는 능력을 보지 않는다.** `gate_cap`이 `legacy=True`로 불려 구성원이면 통과한다. 예외는 조직 전체 공유로, legacy에서도 DB 능력을 본다
  (`backend/app/authz/share_rules.py:68-74`).
- 마켓플레이스 설치는 만드는 종류의 능력을 요구한다(스킬→`cap_create_skill`, MCP→`cap_register_mcp`, 에이전트→`cap_create_agent`,
  `backend/app/authz/marketplace_lifecycle.py:54-62`). 설치에 관리자 승인 단계는 없다.

### 2.4 도구 정의 검토 (순번 10, D11)

- 새로 발견된 MCP 도구는 `pending`으로 시작하고 승인 전에는 에이전트에 보이지 않는다. 설명·입력 스키마·주석·서버가 바뀌면 바뀐 정의가 따로 대기한다
  (`review.py:1-40`). 실행 가능 조건은 `enabled and review_state == "approved"`(`review.py:214-216`).
- 승인 권한은 서버의 `can_edit`다(`routers/mcp.py:605-629`). 독스트링은 "관리자만"이라 하지만 편집자도 통과한다.
- 알림은 회사 서버의 관리자에게 가고(`backend/app/mcp/discovery.py:54-68`), **승인함 행은 만들지 않는다**.
- `mcp_tools.enabled`를 바꾸는 API·화면은 없다(표시만 한다).
- 마켓플레이스로 설치한 MCP 서버의 도구는 게시자가 승인한 스냅숏으로 들어와 이미 승인된 것으로 친다(`backend/app/marketplace/install/mcp.py:150-169`).

### 2.5 공유와 공개 범위

- 공유 대상 종류: agent, skill, tool, mcp_server, credential, workflow. 받는 쪽은 사람·그룹·조직, 단계는 consumer/viewer/editor/manager
  (`backend/app/authz/share_targets.py:47-77`, `backend/app/schemas/grant.py:28-34`).
- 화면: 공유 대화상자(`frontend/src/components/sharing/resource-share-dialog.tsx`)가 도구·MCP 서버·스킬·에이전트·자격증명·워크플로에서 열린다.
- 목록: 종류가 enforce가 아니면 옛 결과(소유자 것, 도구는 시스템 도구 포함)를 그대로 낸다. enforce면 후보를 권한 검사로 거른다(`resource_gate.py:140-166`).
- 플랫폼(시스템) 리소스: 회사·조직이 `catalog_policy`로 끌 수 있다(`backend/app/schemas/org_catalog.py:9-32`, `backend/app/routers/tenant_catalog.py:36-60`).
  효과는 권한 튜플 전개로만 나가므로 **legacy에서는 적용되지 않는다**(`backend/app/authz/catalog_fanout.py:204-205`).
- 승인함 요청 종류는 `tool`과 `business` 둘이다(`backend/app/models/approval_request.py:42-57`).
- 긴급 중지는 에이전트·사용자·MCP 서버 단위로 있고 호출 시점에 막는다(`backend/app/approvals/emergency.py:118-129,434`).

### 2.6 스킬, 하위 에이전트, A2A

- 스킬에는 스킬별 승인·위험 설정이 없다. 모든 스킬 실행이 도구 하나 `execute_in_skill`(코드 실행 등급)로 묶인다(`risk.py:259-268`).
- 하위 에이전트: 공유받은 에이전트를 붙이는 것은 `can_run`으로 확인한다(`backend/app/authz/attach_candidates.py:57-73`). 하위 에이전트 자신의
  도구 승인 설정은 적용되지 않는다(회사 계층만).
- A2A 구현은 없다(테스트의 이벤트 이름과 문서 언급뿐).

## 3. 설계

### 3.1 원칙

1. **판정은 계속 한 함수**(`tool_modes.decide`)에서 한다. 계층을 더할 뿐 새 경로를 만들지 않는다.
2. **구체적인 설정이 넓은 설정을 이긴다.** 도구별 > 서버별 > 위험 등급. 에이전트 도구별 > 실행 경로 모드.
3. **회사가 정한 범위 밖으로는 어떤 설정도 못 나간다.** 저장할 때 거부하고, 실행할 때 다시 확인한다.
4. **설정은 이름이 아니라 리소스 식별자에 붙는다.**
5. **권한 모드(legacy/enforce)에 따라 답이 달라지는 규칙을 만들지 않는다.** 이 문서의 규칙은 DB에서 직접 확인한다. 예외는 3.6에 적는다.
6. 리소스 종류마다 다른 것은 "위험 등급을 어떻게 아는가"와 "정의가 바뀐 것을 어떻게 아는가" 둘뿐이고, 나머지는 공통이다(3.8).

### 3.2 리소스 식별자

설정 키를 이름에서 식별자로 바꾼다.

| 종류 | 키 | 비고 |
|---|---|---|
| MCP 도구 | `mcp:<mcp_tools.id>` | 서버가 달라도 겹치지 않는다 |
| MCP 서버 | `mcp_server:<mcp_servers.id>` | 서버 단위 기본값용 |
| 등록·시스템 도구 | `tool:<tools.id>` | |
| 내장 도구 | `builtin:<이름>` | `write_file`, `edit_file`, `execute`, `web_search` 등 |
| 스킬(6단계) | `skill:<skills.id>` | |
| 하위 에이전트(6단계) | `agent:<agents.id>` | |

- 실행 때 만들어지는 도구 객체의 메타데이터에 키를 싣는다(위험 등급을 싣는 자리와 같다). `decide`는 이름 대신 키로 설정을 찾는다.
  이름이 `srv_…`로 바뀌어도 키는 그대로다(2.2의 결함이 없어진다).
- 에이전트 설정 `tool_approval.tools`의 키를 식별자로 옮긴다. 옛 이름 키는 읽을 때 그 에이전트에 붙은 도구에서 **하나로 정해질 때만** 식별자로 바꿔 읽고,
  둘 이상에 맞으면 버리지 않고 "확인 필요"로 화면에 띄운다. 다음 저장 때 식별자로 쓴다.
- 회사 `always_ask_tools`(이름 목록)는 그대로 읽되 새 표(3.4)가 우선한다. 화면의 자유 입력은 도구 선택기로 바꾼다.
- 에이전트를 복제하거나 마켓플레이스에서 설치하면 도구 행이 새로 생기므로 **키를 새 행으로 바꿔 적는다**. 바꿀 수 없는 키는 지우고 설치 결과에 알린다.

### 3.3 도구 자체의 기본값

- 열 추가: `mcp_servers.approval_default`, `mcp_tools.approval_default`, `tools.approval_default`. 값은 `always`/`when`/`never` 또는 비움.
  `when`은 조건 규칙을 함께 저장한다(에이전트 설정과 같은 `Condition`, 도구 인자만 읽는다).
- 정하는 사람: 그 도구(서버)를 편집할 수 있는 사람(`can_edit`). 화면은 도구 상세·MCP 서버 상세.
- 찾는 순서: 도구 값 → 서버 값 → 위험 등급 기본값.
- 이것은 **기본값일 뿐 바닥이 아니다.** 에이전트에 붙이는 사람이 바꿀 수 있다(1.1의 1번). 공유한 도구에 바닥을 두고 싶으면 회사 정책(3.4)을 쓴다.
- 지식 도구: 내부 지식 서버의 읽기 도구는 위험 등급 자체를 읽기 전용으로 본다(`mcp_servers.kind`가 내부 서버일 때, Mycelium v2 10장 선행 작업).
  그래서 기본이 "묻지 않기"이고 예약 실행도 된다. 바꾸고 싶으면 이 기본값이나 에이전트 설정에서 `always`로 둔다.

### 3.4 회사의 도구별 정책

새 표 `resource_policies`.

| 열 | 뜻 |
|---|---|
| `tenant_id`, `org_id`(없으면 회사 전체) | 범위. 조직 값은 회사 값이 허용한 범위 안에서만 좁힌다 |
| `resource_type`, `resource_id` | 3.2의 식별자. MCP 서버 단위로도 둘 수 있다(그 서버의 모든 도구) |
| `enabled` | 거짓이면 사용 금지 |
| `default_mode` | 회사 기본값. 비우면 도구 자체 기본값을 따른다 |
| `allowed_modes` | 허용 단계 집합. 비우면 셋 다 허용 |
| `rule` | `default_mode`가 `when`일 때의 조건 |
| `updated_by`, `updated_at` | |

- **기본값, 금지, 강제를 한 모양으로 표현한다.** 허용 셋 = 자유, 허용 둘 = 한 단계 금지, 허용 하나 = 그 값으로 고정.
- 검증: `default_mode`는 `allowed_modes` 안에 있어야 한다. 허용이 하나면 기본값은 그 값이다.
- 위험 등급별 동작(지금 있는 것)과의 관계: **도구별 정책이 등급별 동작보다 우선한다.** 둘 다 회사 관리자가 정한 것이고 도구별이 더 구체적이다.
  등급 `block`인데 도구별로 `enabled=true`를 명시하면 그 도구만 쓸 수 있다. 화면은 이 경우 "등급 정책의 예외"라고 표시한다.
- 지금 있는 것을 같은 말로 읽으면:
  등급 `approval` = 그 등급 전체가 `always` 고정, `approval_relaxable` = 기본 `always`·셋 다 허용, `allow` = 기본 `never`, `always_ask_tools` = 도구별 `always` 고정.
  데이터는 옮기지 않고 판정에서만 이렇게 읽는다.
- 정하는 사람: 회사 관리자(지금 가드레일 설정과 같은 `GOVERNANCE`), 조직 값은 조직 정책 관리자(`can_manage_policy`).
- 화면: 회사 설정 > 가드레일 아래 "도구별 정책" 표. 도구를 고르고 기본값과 허용 단계를 체크한다. 서버 행에서 "이 서버의 모든 도구"로 한 번에 둔다.
- 실행별 고정: 실행에 실린 도구의 정책 행을 지금의 가드레일 스냅숏에 함께 넣는다. 재개는 처음 답을 따른다.

### 3.5 판정 순서 (새 `decide`)

| 순서 | 계층 | 결과 | 비고 |
|---|---|---|---|
| 1 | 긴급 중지, 등록 미승인(3.7), 사용자·팀 금지(3.6) | 실행 불가 | 승인 판정보다 앞. 지금 위치 그대로 |
| 2 | 회사 사용 금지(도구별 `enabled=false`, 없으면 등급 `block`) | 숨김 | |
| 3 | 회사 고정(허용 단계가 하나, 또는 도구별 정책이 없고 등급 `approval`·`always_ask_tools`) | 그 값 | 아래 어떤 설정도 못 바꾼다 |
| 4 | 에이전트 도구별 설정 | 그 값 | 허용 단계 안일 때만. 밖이면 무시하고 다음으로 |
| 5 | 옛 `human_in_the_loop` 설정 | 묻기 | 지금과 같다 |
| 6 | 대화 허용("이 대화 동안 허용") | 자동 | `never`가 허용될 때만 |
| 7 | 회사 도구별 기본값 | 그 값 | |
| 8 | 도구 자체 기본값(도구 → 서버) | 그 값 | 허용 단계 안일 때만 |
| 9 | 실행 경로 모드 `auto` | 자동 | `never`가 허용될 때만 |
| 10 | 위험 등급 기본값 | 읽기 전용은 자동, 나머지는 묻기 | 결과가 허용 단계 밖이면 회사 기본값 |

- 4~9는 "구체적인 것이 먼저"다. 도구에 명시한 기본값(7, 8)은 에이전트 전체에 건 `auto`(9)보다 구체적이므로 이긴다.
  그래서 도구 주인이 `always`로 둔 도구는 에이전트를 `auto`로 돌려도 묻고, 풀려면 그 도구를 4에서 직접 `never`로 둬야 한다.
- 하위 에이전트: 지금 규칙을 넓힌다. **조이는 값(`always`, `when`)은 모든 에이전트에, 푸는 값(`never`, 대화 허용, `auto`)은 루트에만** 적용한다.
  회사 계층(2, 3, 7)은 푸는 값이어도 모든 에이전트에 적용한다(회사가 정한 것이므로).
- 예약 실행: 도구가 예약에서 막히는지는 고정 표시(`trigger_safe`)가 아니라 **판정 결과**로 정한다. 결과가 자동이면 실행하고, 묻기면 그 예약의 승인 정책
  (`inbox`는 승인함 대기, `blocked`는 막음)을 따른다. 지금은 MCP 도구가 일괄로 막혀 회사가 `never`로 고정해도 예약에서 못 쓴다.
- `Decision.layer`에 새 값(`company_tool_locked`, `company_tool_default`, `tool_default`, `server_default`)을 더해 "실제 적용" 표와 승인 카드에 나간다.
- 임대 실행 경로는 푸는 설정이 있으면 일반 경로로 돌아가는 지금 규칙을 그대로 따른다(`approval-modes-plan.md` 8장).

### 3.6 등록 권한과 공개 범위

**회사 설정 `registration`** (리소스 종류마다: `mcp_server`, `tool`, `skill`, `agent`)

| 항목 | 값 | 뜻 |
|---|---|---|
| `who` | `members` / `granted` | 구성원 누구나 / 능력을 가진 사람만(역할 builder 이상 + 개별 부여) |
| `review` | `off` / `on` | 등록 즉시 사용 / 관리자 승인 뒤 사용. 능력을 가진 사람의 등록은 검토 없이 통과 |
| `member_sharing` | `private` / `shareable` | 직원 등록분을 본인만 / 사람·팀에 공유 가능 |

- "관리자만 등록" = `who: granted`이고 아무에게도 부여하지 않음. "특정 팀만 등록" = `who: granted`이고 그 그룹에 능력 부여(지금 화면으로 된다).
  "직원도 등록, 승인 필요" = `who: members`, `review: on`.
- 기본값: `who: members`, `review: off`, `member_sharing: shareable`. 지금 동작과 같다.
- **확인은 DB 능력으로 한다.** `who: granted`면 권한 모드와 상관없이 `org_permissions`의 능력을 본다(조직 전체 공유가 지금 그렇게 한다).
  enforce 모드에서는 지금처럼 권한 서비스도 함께 본다.
- 마켓플레이스 설치, 블루프린트 가져오기, 대화형 빌더·어시스턴트의 쓰기 도구처럼 **리소스를 만드는 모든 경로**가 같은 확인을 거친다.
  등록 승인이 켜져 있으면 설치로 만든 것도 승인 대기로 들어간다.
- `member_sharing: private`이면 공유 API가 그 리소스의 공유를 거부한다(관리자가 소유권을 회사로 옮긴 뒤 공유하는 길은 열어 둔다, 지금 있는 이전 기능).

**사람·팀 지정**

- 회사가 등록한 도구는 지금 공유 기능으로 사람·그룹·조직에 `consumer`를 준다. 새 저장 구조는 없다.
- 서버 안의 도구 하나를 특정 사람·팀에게만 막는 것은 모델에 이미 있는 `mcp_tool.blocked`를 쓴다. 쓰는 API와 화면(서버 상세의 도구 표)을 더한다.
- **이 부분은 enforce 모드가 필요하다.** legacy의 목록은 소유자 것만 내므로 관리자가 등록한 도구가 다른 사람에게 보이지 않는다.
  그래서 회사 테넌트는 `mcp_server`, `tool`, `skill`, `agent` 종류를 enforce로 돌리는 것을 전제로 한다(G2). 개인 테넌트는 혼자 쓰므로 필요 없다.
- 플랫폼(시스템) 도구를 회사가 끄는 것(`catalog_policy`)도 enforce에서만 듣는다. 이 문서의 `resource_policies.enabled`는 실행 때 DB로 직접 확인하므로
  legacy에서도 듣는다. 시스템 도구 끄기를 이쪽으로 합치는 것은 5단계에서 한다.

### 3.7 등록 승인

- 상태 열: `mcp_servers.registration_state`, `tools.registration_state`(뒤에 `skills`, `agents`). 값은 `approved`/`pending`/`rejected`. 기본 `approved`.
- `review: on`인 회사에서 능력이 없는 사람이 등록하면 `pending`으로 만들어진다.
  - 등록한 사람은 그 리소스를 보고 설정을 고치고 **연결 시험**(도구 목록 가져오기)을 할 수 있다. 관리자가 무엇을 승인하는지 보려면 목록이 있어야 한다.
  - `pending`·`rejected`는 에이전트에 붙일 수 없고, 이미 붙어 있어도 실행에 실리지 않는다(도구 정의 검토와 같은 자리에서 거른다).
- 승인함: 요청 종류 `registration`을 더한다. 대화도 워크플로 단계도 가리키지 않고 리소스를 가리킨다.
  승인 요청을 읽는 코드는 지금도 `kind`로 갈라야 하고(`business` 행에는 대화가 없다), 같은 규칙을 따른다.
  결정자는 회사 관리자와 그 조직의 관리자다. 결정은 지금 승인함의 compare-and-set을 그대로 쓴다.
- 승인 카드에 보이는 것: 서버 주소(또는 실행 명령), 전송 방식, 쓰는 자격증명의 이름, 도구 목록과 각 도구의 설명·읽기 전용 표시, 등록자.
  도구 설명은 외부에서 온 글이므로 화면에 글자로만 보여 주고 링크·서식을 살리지 않는다.
- **다시 승인받는 경우**: 서버의 주소·실행 명령·전송 방식·인증 방식이 바뀌면 `pending`으로 돌아간다(이 값들의 지문을 승인 때 저장한다).
  이름·설명·아이콘 변경은 해당하지 않는다.
- **도구 정의 검토와 잇기**: `review: on`인 회사에서 직원이 등록한 서버는 새 도구·바뀐 정의의 승인도 관리자에게 간다(서버 주인 본인 승인으로 끝나지 않는다).
  이렇게 하지 않으면 승인받은 뒤 도구 설명을 바꾸는 것으로 등록 승인을 피해 간다(부록 A의 "승인 후 변경").
  회사가 등록한 서버와 `review: off`인 회사는 지금처럼 서버 관리자가 승인한다.
- 승인된 정의가 바뀌어도 그 도구의 승인 설정(에이전트·회사)은 유지한다. 바뀐 정의는 승인 전까지 쓰이지 않으므로 설정이 옛 정의에만 적용된다.
  도구가 서버에서 사라졌다가 같은 이름으로 다시 나타나면 같은 행(같은 키)으로 본다(지금 검토 로직이 그렇게 한다).
- 거절되면 등록자에게 사유와 함께 알린다. 등록자는 고쳐서 다시 요청할 수 있다.

### 3.8 스킬, 하위 에이전트, A2A에 같은 틀 쓰기

공통: 식별자(3.2), 도구 자체 기본값(3.3), 회사 정책 표(3.4), 판정 순서(3.5), 등록 설정과 공개 범위(3.6), 등록 승인(3.7).
종류마다 다른 것은 아래 표뿐이다.

| 종류 | 위험 등급을 아는 곳 | 정의가 바뀐 것을 아는 곳 | 호출을 식별하는 방법 | 지금 빠진 것 |
|---|---|---|---|---|
| MCP 도구 | 서버 종류·주석·이름 규칙(`mcp_tool_risk`) | 도구 정의 지문(있음) | 도구 객체의 키 | 3.2~3.7 |
| 등록·시스템 도구 | 도구 정의(코드) | 코드 배포 | 도구 객체의 키 | 3.2~3.4 |
| 스킬 | 코드 실행 등급 고정. 스킬별로 낮추지 않는다 | `content_hash`(있음) | `execute_in_skill` 호출의 스킬 인자에서 키를 찾는다 | 스킬별 설정, 호출 인자로 키 찾기 |
| 하위 에이전트 | 그 에이전트가 가진 도구 중 가장 높은 등급 | 설정 버전 | 위임 도구 호출의 대상 에이전트 | 위임 전 승인, 공유받은 에이전트의 설정 변경 알림 |
| A2A 원격 에이전트 | 외부 변경 등급 고정 | 에이전트 카드 지문 | 원격 에이전트 식별자 | 구현 전체 |

- 스킬: 모든 스킬이 도구 하나로 실행되므로, 승인 항목의 조건 함수가 호출 인자의 스킬을 보고 그 스킬의 키로 `decide`를 부른다.
  조건 함수는 재개 때 다시 불리므로 같은 입력에 같은 답을 내야 한다(가드레일 승인 규칙과 같은 제약).
- 하위 에이전트: "이 에이전트에게 맡기기 전에 묻기"를 같은 세 단계로 둔다. 하위 에이전트 안의 도구는 3.5의 하위 에이전트 규칙을 따른다.
- A2A: 원격 에이전트 등록은 MCP 서버 등록과 같은 절차(등록 설정, 등록 승인, 카드 지문으로 다시 승인)를 쓴다. A2A 규격은 카드 서명을 선택으로 두고
  권한 판단을 구현에 맡기므로(부록 A), 거버넌스는 전부 Moldy 쪽에서 한다. 이 문서는 표의 계약만 정한다.

### 3.9 화면

- **도구·MCP 서버 상세**: "승인 기본값" 선택. 회사가 잠갔으면 비활성으로 보이고 "회사 정책으로 고정됨"이 표시된다. 등록 상태 배지(승인 대기·거절).
- **에이전트 설정 > 도구 승인**(지금 있는 화면): 도구마다 지금 값의 출처를 보여 준다(회사 고정 / 에이전트에서 바꿈 / 회사 기본값 / 도구 기본값 / 위험 등급).
  허용되지 않은 단계는 고를 수 없고 이유가 툴팁에 나온다.
- **회사 설정 > 가드레일 > 도구별 정책**: 3.4의 표.
- **회사 설정 > 등록**: 3.6의 종류별 세 항목. 능력 부여는 지금의 역할 화면으로 연결한다.
- **승인함**: 등록 요청 카드(3.7).
- **개인 테넌트**: 회사 설정 화면을 보이지 않는다. 등록 설정은 기본값으로 고정이고, 도구 자체 기본값과 에이전트 설정만 쓴다.

### 3.10 기록과 감사

- 감사 동작: `resource_policy.updated`(전·후 값), `registration.settings_updated`, `registration.requested`/`approved`/`rejected`/`reset`(다시 승인 대기로 돌아감),
  `tool.approval_default_updated`, `mcp_tool.block_updated`. 각 동작은 내용(행동·결과·사유·대상)을 단언하는 테스트를 함께 둔다.
- 승인 카드와 `approval.auto_allowed` 기록의 이유 계층에 3.5의 새 값이 실린다.
- 회사 정책을 조이는 저장 전에 **영향 미리 보기**를 보여 준다: 이 변경으로 설정이 무시되는 에이전트 수와 목록. 조직 카탈로그 정책의 `/impact`와 같은 모양이다.

### 3.11 실행 계약 (ADR-024)

| 항목 | 내용 |
|---|---|
| 판정 위치 | `app/approvals/tool_modes.decide` 하나. 실행 조립과 "실제 적용" API가 같은 함수를 쓴다 |
| 실행 중 변경 | 회사 정책·도구 기본값 변경은 다음 실행부터. 실행 중인 것은 고정된 스냅숏을 따른다 |
| 즉시 반영 | 사용 금지(`enabled=false`), 등록 승인 취소, 사용자·팀 금지, 긴급 중지는 호출 시점에 확인해 실행 중에도 막는다 |

## 4. 요구에 없었지만 정해야 하는 것

사용자 요구(1.1)에 없던 것 중, 정하지 않으면 구멍이 되는 것들이다. 각 항목의 답은 3장과 5장에 있다.

1. **이름 충돌**: 지금도 있는 결함이다. 도구별 설정을 믿으려면 식별자가 먼저다(3.2).
2. **권한 모드**: 등록 제한과 사람·팀 지정이 legacy에서 듣지 않는다(2.3, 2.5). 회사 테넌트의 전제를 정해야 한다(G2).
3. **승인 뒤 변경**: 등록 승인만 두면 승인 뒤에 주소나 도구 설명을 바꿔 피해 간다(3.7).
4. **정책을 조일 때 이미 있는 에이전트**: 저장된 설정을 지우지 않고 실행 때 무시하며, 화면에 표시한다. 조이기 전에 영향을 보여 준다(3.10).
5. **실행 중인 실행**: 승인 단계는 다음 실행부터, 사용 금지는 즉시(3.11).
6. **예약·API·워크플로**: 고정 표시 대신 판정 결과로 정한다(3.5).
7. **하위 에이전트**: 푸는 값은 루트만(3.5).
8. **복제·마켓플레이스 설치**: 키를 새 행으로 바꿔 적어야 한다. 설치받은 회사의 정책이 게시자의 설정보다 우선한다(3.2, 3.5).
9. **공유받은 에이전트**: 실행하는 사람은 승인 설정을 바꿀 수 없고, 편집 권한이 있는 사람만 바꾼다. 실행은 **실행하는 사람 회사**의 정책을 따른다.
10. **누구의 자격증명으로 부르나**: 팀에 준 MCP 서버는 서버에 묶인 자격증명 하나로 불린다. 받은 사람 모두가 등록자의 권한으로 외부 시스템을 쓰게 된다.
    다른 플랫폼도 이것을 따로 경고한다(부록 A). 공유 대화상자에 경고를 넣고, 사용자별 자격증명은 이 문서 범위 밖으로 둔다(G11).
11. **등록자가 떠날 때**: 직원 등록분은 소유권 이전(지금 있음)으로 회사가 넘겨받거나 함께 정리한다. 퇴사 처리에서 이 목록을 보여 준다(G12).
12. **새 도구의 기본 상태**: 다른 플랫폼은 "새로 생긴 도구를 켤지"를 관리자 설정으로 둔다. Moldy는 도구 정의 검토가 이미 그 역할을 한다(승인 전에는 안 보임).
    서버 단위 회사 정책(3.4)이 새 도구에도 바로 적용되므로 따로 두지 않는다.
13. **조건부(`when`)를 회사가 쓰는 경우**: 회사 기본값이 `when`이면 조건 규칙도 회사가 정한다. 에이전트 쪽이 `when`을 고르면 자기 조건을 쓰되,
    회사가 `never`를 금지했다면 "항상 거짓" 조건으로 사실상 `never`를 만드는 것을 막아야 한다(G6).
14. **승인 피로**: 전부 "항상 묻기"로 고정하면 승인이 형식이 된다. 회사 화면에 "읽기 전용 도구는 묻지 않기 권장"을 안내하고, 승인 요청 수를 도구별로 보여 준다.
15. **검토 권한 표기**: 도구 정의 검토 API가 "관리자만"이라 적고 편집자도 통과시킨다(2.4). 어느 쪽이 맞는지 정한다(G13).

## 7. 검증

- **판정 표 테스트**: 3.5의 계층 조합을 표로 만들어 `decide`의 결과와 이유 계층을 명시적 기대값으로 고정한다. 계층 하나를 빼는 변이를 넣어 실패하는지 확인한다.
- **이름 충돌**: 두 서버가 같은 이름의 도구를 낼 때 각 도구의 설정이 따로 적용되는지(지금은 실패하는 테스트로 먼저 쓴다).
- **저장과 실행 양쪽**: 허용되지 않은 단계가 저장에서 거부되는 것과, 이미 저장된 값이 실행에서 무시되는 것을 각각 테스트한다(create와 update 따로).
- **권한 모드**: 등록 제한과 승인 단계가 legacy와 enforce에서 같은 답을 내는지 두 모드로 돌린다.
- **만드는 경로 전수**: 직접 등록, 마켓플레이스 설치, 블루프린트, 어시스턴트 쓰기 도구가 모두 등록 설정을 거치는지 경로별 테스트.
- **다시 승인**: 주소를 바꾸면 `pending`으로 돌아가고 그 도구가 실행에서 빠지는지. 이름만 바꾸면 그대로인지.
- **재개**: 정책을 바꾼 뒤 멈춰 있던 실행을 재개하면 처음 답을 내는지.
- **승인함**: `registration` 행이 대화·워크플로를 가정하는 기존 읽기 경로를 깨지 않는지(목록, 상세, 만료, 긴급 중지).
- **E2E**: 직원이 서버 등록 → 관리자가 승인함에서 승인 → 직원이 에이전트에 붙임 → 회사가 `always` 고정 → 에이전트 설정에서 잠겨 보이고 실행에서 묻는다.
- 감사 동작마다 내용 단언 테스트(`tests/test_audit_integration.py`).

## 8. 위험

| 위험 | 대응 |
|---|---|
| 키를 옮기다 기존 설정이 사라진다 | 옛 이름 키를 지우지 않고 읽는다. 하나로 정해지지 않으면 화면에 띄운다. 옮기기 전후의 판정 결과를 비교하는 테스트 |
| 회사가 위험한 도구를 `never`로 고정한다 | 허용한다(회사의 결정). 저장할 때 등급과 함께 경고하고 감사에 남긴다 |
| 등록 설정을 `granted`로 바꾸자 직원이 에이전트를 못 만든다 | 종류별로 따로 정한다. 바꾸기 전에 능력을 가진 사람 수를 보여 준다 |
| enforce로 바꾸는 것이 회사마다 부담이다 | 등록 제한·승인 단계·등록 승인은 모드와 무관하게 만든다. enforce가 필요한 것은 사람·팀 지정뿐이라고 화면에 밝힌다 |
| 승인함 새 종류가 기존 코드를 깬다 | `kind`로 가르는 자리를 전수로 찾아 테스트로 잠근다(`business`를 넣을 때와 같은 방법) |
| 하위 프로세스·임대 실행에서 판정이 달라진다 | 임대 경로는 푸는 설정이 있으면 일반 경로로 돌아간다. 새 계층도 같은 규칙에 넣는다 |
| 판정 계층이 늘어 설명이 어렵다 | "실제 적용" 표가 결과와 이유 계층을 한 줄로 보여 준다. 화면 문구는 계층 이름이 아니라 "회사 정책으로 고정됨"처럼 쓴다 |

Moldy 설계에 가져온 것
- 세 단계와 "거부가 이긴다", "회사가 상한이고 아래는 좁히기만"은 거의 모든 곳이 같다.
- 커넥터 안의 개별 도구를 따로 다루는 것(Power Platform, ChatGPT, Claude)과 서버 단위로 한 번에 두는 것을 함께 둔다(3.4).
- 이름으로 통제하면 우회된다(GitHub이 스스로 밝힘). 식별자를 쓴다(3.2).
- 등록과 게시(사용 허가)를 나눈다(ChatGPT의 초안 → 관리자 게시). 등록 승인이 그 자리다(3.7).
- 무인 실행은 "거부"와 "멈추고 기다림" 둘 중 하나다. Moldy는 둘 다 이미 있다.

Moldy가 직접 정한 것(다른 곳에서 확인되지 않은 것)
- 승인된 도구의 정의가 바뀌면 다시 승인받는 절차. MCP 규격은 목록 변경 알림만 정의하고, 주석은 "신뢰할 수 있는 서버에서 온 것이 아니면 믿지 말라"고 적는다.
  설명문에 지시를 숨기거나 승인 뒤 설명을 바꾸는 공격이 2025년에 공개됐다(요약). Moldy는 도구 정의 검토가 있고, 3.7에서 등록 승인과 잇는다.
- 스킬·하위 에이전트·원격 에이전트를 같은 틀로 다루는 것. A2A 규격은 카드 서명을 선택으로 두고 권한 판단을 구현에 맡긴다.

확인하지 못한 것: Glean, Agentforce, Slack, Zapier, Vertex Agent Builder(조사 못 함). VS Code의 승인 단계와 정책 키, ChatGPT의 액션 변경 표시와 예약 실행 중
승인 대기 동작(요약만). Claude가 읽기·쓰기 묶음을 매기는 방법(문서에 없음).
