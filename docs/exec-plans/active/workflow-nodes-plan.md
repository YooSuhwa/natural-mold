## 1. 목표와 완료 기준

1. 아래 노드를 편집기에서 만들고(노드 추가, 설정 패널, 검사), 게시하고, 실행하면 실행 상세에 단계와 결과가 남는다.
2. 각 노드는 ADR-026의 복구 규칙을 지킨다: 끝난 단계는 다시 실행하지 않고, 바깥에 영향을 주는 단계가 실행 중 끊기면 결과 불명으로
   사람에게 묻는다.
3. 모델을 부르는 노드(LLM 판단, LLM 호출, 병렬 안 에이전트, 항목마다)는 사용 한도를 넘으면 시작하지 않는다.
4. AI 편집이 새 노드를 쓸 수 있고(시스템 프롬프트·평가), 시험 모델로 E2E가 돈다.

## 2. 노드

| 노드 | 하는 일 | 출력 | 갈래 |
|---|---|---|---|
| **여러 갈래 판단** `switch` | 값 하나를 보고 경우(case)마다 다른 갈래로. 경우는 "값이 X와 같음" 목록, 나머지는 `default` | `{value, case}` | 경우 이름마다 + `default` |
| **판단(LLM 방식)** `decision_bool` + `evaluator: "llm"` | 질문 템플릿을 시스템 모델에 물어 예/아니오와 확신도 | `{value, confidence, band, evaluator: "llm", reason}` | 예·아니오(반복 갈래 규칙 그대로) |
| **LLM 호출** `llm` | 에이전트 없이 시스템 모델에 한 번 묻기(요약·변환·추출). 출력 형식은 에이전트 노드와 같은 스키마 | 스키마의 값 | 하나 |
| **사람에게 묻기** `ask` | 실행자에게 질문을 보내고(승인함) 글로 답을 받음. 기한 필수, 넘으면 `timeout` 갈래 | `{answer}` | `answered`·`timeout` |
| **알림** `notify` | 실행자에게 앱 알림 한 건(제목·본문 템플릿). 실행은 멈추지 않음 | `{sent: true}` | 하나 |
| **항목마다** `for_each` | 앞 단계의 목록 값의 항목마다 같은 에이전트를 실행해 결과 목록으로(최대 20개) | `{items: [...], count}` | 하나 |
| **병렬 에이전트** `parallel` | 같은 입력으로 에이전트 여럿(최대 5)을 동시에 실행하고 결과를 이름별로 합침 | `{<branch>: <출력>}` | 하나 |
| **도구 호출** `tool` | 읽기 전용 기본 도구 하나를 바로 호출(웹 검색, 웹 페이지 읽기, 현재 시각) | 도구 결과 | 하나 |
| **파일 입력** 입력 타입 `file` | 실행할 때 파일을 올리고, 에이전트 단계가 그 파일을 첨부로 받음 | 입력 값 = 업로드 ID | — |

## 3. 설계

### 3.1 실행 원칙

- 모든 노드는 지금처럼 **단계 행 하나**로 기록된다. `for_each`와 `parallel`은 한 단계 안에서 여러 에이전트 실행을 하되, 하위 실행마다
  `workflow_step_runs`에 **하위 행**을 둔다(`parent_step_id`, `branch_key`): 하위 행이 에이전트 실행의 봉투다(기존 에이전트 단계와 같은
  접수·결과 불명 규칙). 부모 단계는 하위 행이 모두 끝나면 결과를 모아 완료된다.
- 끊긴 뒤 재확보: 끝난 하위 행은 다시 실행하지 않고, 실행 중이던 하위 행은 결과 불명(부모 단계도 결과 불명, 기존 확인 요청).
- 모델을 부르는 단순 노드(`llm`, LLM 판단)는 바깥 부작용이 없으므로 끊기면 **다시 실행한다**(결과 불명으로 묻지 않음). 비용만 든다.
- `tool`은 **읽기 전용 기본 도구만**(N7) 허용해 "바깥 부작용은 에이전트 단계 안에서만"(workflow-plan 3.5)을 지킨다. 끊기면 다시 실행.
- `notify`는 같은 단계 행에 알림을 한 번만 보낸다(단계 행이 이미 있으면 보내지 않음).

### 3.2 정의 스키마

- `SwitchNode`: `source`·`path`(판단 대상 값), `cases`: `[{name, value}]`(1~10, 이름은 식별자), 갈래 `when`은 case 이름 또는 `default`.
- `DecisionNode.evaluator`: `rule`(기본) | `llm`. `llm`이면 `question` 템플릿 필수, `condition` 없음.
- `LlmNode`: `prompt` 템플릿, `output_schema`(에이전트 노드와 같은 부분집합).
- `AskNode`: `question` 템플릿, `timeout_minutes` 필수.
- `NotifyNode`: `title`·`body` 템플릿.
- `ForEachNode`: `source`·`path`(배열), `agent_id`, `prompt`(항목은 `{"ref": {"node": "item", "path": ""}}`), `output_schema`, `max_items` ≤ 20.
- `ParallelNode`: `branches`: `[{name, agent_id, prompt, output_schema}]`(2~5).
- `ToolNode`: `tool`: `web_search` | `web_scraper` | `current_datetime`, `args` 템플릿 맵.
- 입력 `type: "file"`: 값은 업로드 ID. 참조하면 에이전트 프롬프트에는 파일 이름이 들어가고 파일은 그 단계 대화의 첨부로 연결된다.
- 갈래 이름 `EdgeWhen`에 `answered`, `timeout`과 switch의 case 이름이 더해진다(갈래 이름은 노드 종류별로 검사).

### 3.3 검사

- `switch`: 경우 이름 중복 금지, 모든 경우와 `default` 연결 필수, 반복의 출발점은 될 수 없음(판단 노드만).
- `ask`: 기한 필수, `answered`·`timeout` 연결 필수. 반복 안에 둘 수 없음(승인과 같은 이유).
- `for_each`: `source`가 배열 값(스키마로 확인), 참조 `item`은 이 노드 안에서만.
- `parallel`: 이름 중복 금지, 에이전트마다 기존 에이전트 검사(보관·권한·도구 호출 모델).
- 지문 고정(Q1)은 `for_each`·`parallel`의 에이전트도 포함한다.

### 3.4 화면

- 노드 추가 목록과 아이콘, 설정 패널(노드별 칸), 카드 한 줄 요약, 실행 상세(하위 행은 단계 아래 펼침), 버전 비교(그대로).
- 사람에게 묻기: 승인함과 실행 상세 카드에 답 입력칸.

## 5. 구현 메모 (2026-11-09)

- 정의: `app/workflows/definition.py`(새 노드, `EdgeWhen`은 식별자 문자열, `agent_uses`가 에이전트를 쓰는 모든 노드를
  한 목록으로). 검사: `checks.py`(갈래·필드·`item` 범위·목록 대상). 고정 핀 키는 노드 ID, 병렬은 `노드.갈래`.
- 실행: 모델·도구 노드는 `node_steps.py`(트랜잭션 밖, 끊기면 다시 실행, 사용량은 실행자), 항목마다·병렬은
  `fanout.py`(하위 행, 묶음 실행, 묶음 사이에는 진행 중인 실행이 없음). 하위 실행 안에서 승인이 필요한 도구는
  막는다(`block`): 부모 단계에는 하나의 재개 지점이 없다. 결과 불명 하위 행은 하나씩 확인을 묻는다.
- 사람에게 묻기: 승인함 업무 요청 `workflow_ask`, 결정은 `approve` 하나에 답 글(빈 답은 422 `answer_required`).
- 알림: 알림 종류 `workflow.notify`(i33), 단계마다 따로(병합 안 함), 대상은 `workflow_run`(실행자 본인 전용).
- 파일 입력: 실행 시작 때 실행자의 보내지 않은 업로드만 받고 `message_id`로 표시(미전송 정리에서 제외),
  `workflow_runs.files`에 ID를 둔다. 참조하는 에이전트 단계마다 파일을 복사해 그 단계 대화의 첨부로 붙인다
  (대화 삭제가 원본을 지우지 않게). 채팅 도구에는 파일 입력을 주지 않는다(필수면 시작을 거절).
- 마이그레이션: i32(하위 행 열, 노드 ID·갈래 폭, 실행 파일), i33(알림 종류).
- 시험 모델은 배열을 두 항목으로 답해 항목마다가 두 번 돈다(`e2e/workflow-nodes.spec.ts`).
