# 워크플로를 채팅 도구로 부르기 기획 (확장 1)

- 상태: **초안**, 2026-11-09. 결정 질문 T1~T8(4장)은 추천안을 적어 두었고, 사용자 확인 뒤 확정한다.
- 범위: `workflow-plan.md` 3.9 "확장 1: 도구형". 에이전트 설정에서 게시된 워크플로를 도구로 붙이고, 채팅 중 모델이 그 도구를 부르면
  워크플로가 한 번 실행되어 결과가 도구 결과로 돌아온다. 예약·Agent API에서 부르기, 공유받은 워크플로 부르기는 범위 밖(4장 T6, T7).
- 근거: `workflow-plan.md` 3.9·Q9, ADR-026, 현재 코드 조사(2장, 2026-11-09 `main` 79ba333f).

## 1. 목표와 완료 기준

예: 채팅에서 "이 고객 문의 처리해 줘" → 에이전트가 "고객 문의 답변 초안" 워크플로 도구를 부름 → 채팅에 "워크플로 실행 중" 카드 →
긴급 문의라 승인 대기면 카드와 승인함에 승인 요청 → 승인 → 워크플로가 끝나면 그 출력으로 채팅이 이어져 에이전트가 답한다.

완료 기준:

1. 에이전트 설정에서 내가 실행할 수 있는 게시된 워크플로를 도구로 붙이고 뗄 수 있다. 도구 인자는 그 워크플로의 시작 입력, 도구 결과는
   최종 출력(실패면 사유)이다.
2. 모델이 도구를 부르면 채팅 실행은 멈추고(`interrupted`), 워크플로가 끝나면(완료·실패·취소) **사람 입력 없이** 그 결과로 다시 이어진다.
   멈춘 동안 채팅에 워크플로 상태 카드가 보이고 실행 상세로 갈 수 있다.
3. 워크플로 안의 업무 승인은 채팅 카드와 승인함 어디서든 한 번만 결정된다(기존 compare-and-set).
4. 채팅을 멈추면(실행 취소) 워크플로도 취소되고, 워크플로를 취소하면 채팅은 "취소됨" 결과로 이어진다. 한쪽만 남지 않는다.
5. 무한 호출이 생기지 않는다: 워크플로 단계 안·하위 에이전트·예약·API 실행에서는 워크플로 도구가 붙지 않는다.
6. 워크플로 실행은 채팅을 한 사람의 실행으로 기록되고, 어느 채팅 실행이 시작했는지 남는다(감사·실행 목록·사용량).
7. 워크플로가 보관·게시 해제되거나 실행 권한이 없어지면 도구가 사라지고, 붙여 둔 연결은 "끊김"으로 보인다(다른 연결 종류와 같은 방식).

## 2. 현재 코드 (조사 결과)

- **도구 연결.** `agent_tools`·`agent_mcp_tools`·`agent_subagents`·`agent_skills`가 `AgentLinkDelegation`(`required`, `link_status`,
  `broken_reason`)을 공유한다. 런타임에서는 `build_tools_config`(`services/chat/runtime_context.py`)가 설정 dict를 만들고
  `_prepare_runtime_components`(`agent_runtime/runtime_preparation.py`)가 `create_tool_for_runtime`(`tool_factory.py`)로 도구를 만든다.
  새 연결 종류는 연결 테이블, 접근 계획(`authz/runtime_access_planner._LINKS`), `build_tools_config`, 준비 루프, lease 경로
  (`prepared_run_tool_inputs.py`, 기본 꺼짐), 하위 에이전트 조립(`subagents.py`)에 각각 알려야 하고, 워크플로 지문 분류
  (`workflows/pins.py` `PINNED_TABLES`, 시험이 강제)에도 넣어야 한다.
- **하위 에이전트**는 같은 스레드·같은 실행 안에서 `task` 도구로 **동기** 실행된다(`run_path="subagent"`). 워크플로는 job worker에서 돌고
  며칠 기다릴 수 있어 이 방식을 쓸 수 없다.
- **멈춤과 재개.** 인터럽트는 HITL 미들웨어, `ask_user`, 연결 로그인 세 가지다. 실행은 `interrupted`가 되고 재개는 항상
  `input.respond` 처리기(`routers/conversation_protocol_fork._handle_input_respond_command`)가 `Command(resume=…)`로 한다. 승인함
  결정과 만료 처리도 같은 처리기를 HTTP 없이 부른다(`approvals/inbox.py`, 만료는 API 스케줄러). **바깥 작업이 끝나 도구 결과로
  재개하는 길은 없다.** 재개 값 형식 검사(`decision_problem`)는 HITL·로그인만 보고, 프론트는 알 수 없는 인터럽트에 카드를 그리지 않는다
  (`hitl-interrupts.ts standardPayloadFromInterrupt`).
- **재개 뒤 정리.** 재개된 실행이 끝나면 `waiters.settle`이 예약·API·워크플로 단계 대기자를 정리한다.
- **워크플로 실행.** `runner.start_run`은 소유자 확인·게시·입력·에이전트 확인 뒤 `workflow.run` 작업을 넣는다. 끝나는 곳은
  `run_job`의 `_audit_finish`, `fail_unknown`, `cancel_run`의 직접 종료다. `workflow_runs`에는 시작한 채팅 실행을 가리키는 열이 없다.
- **사용량.** 워크플로 단계는 단계마다 `WORKFLOW`로 기록되고, 하위 에이전트는 부모 실행 안에 합산된다(`tenancy/attribution.py`).

## 3. 설계

### 3.1 연결과 도구

- 새 연결 테이블 `agent_workflows`(`agent_id`, `workflow_id`, `AgentLinkDelegation` 열, 유일 `(agent_id, workflow_id)`). 지문 분류는
  **고정**(연결이 바뀌면 그 에이전트를 쓰는 워크플로는 다시 게시).
- 도구는 **부르는 시점의 게시 버전**으로 만든다(T3). 이름 `workflow_<짧은 id>`(ASCII 규칙 `_safe_tool_name`), 설명은 워크플로 이름·설명,
  인자 스키마는 게시 버전의 `inputs`(타입·필수·`max_length`)에서 만든다. 사람에게는 워크플로 이름으로 보인다.
- 도구가 붙는 조건: 채팅 실행(`run_path="chat"`)이고, 채팅한 사람이 그 워크플로를 실행할 수 있고(1차는 소유자, T6), 게시돼 있고
  보관되지 않았을 때. 아니면 도구를 빼고 연결을 `broken`으로 표시한다(완료 기준 7).

### 3.2 부르기: 멈추고, 끝나면 이어 가기

```
모델 → workflow_<id>(inputs)
  도구: runner.start_run(채팅한 사람, inputs, parent_conversation_run_id=이번 채팅 실행)
       → interrupt({"type": "workflow_wait", "workflow_run_id": …, "workflow_id": …})
  채팅 실행: interrupted (기존 경로 그대로, 승인 요청 행은 만들지 않음)
worker: workflow.run … 끝남(완료/실패/취소)
  runner 종료 지점 → "workflow.chat_resume" 작업(run_id 멱등)
  처리기: 부모 채팅 실행이 아직 이 대기로 멈춰 있으면 input.respond(workflow_wait 응답 = {status, output | error})로 재개
채팅: 같은 도구 호출의 결과로 이어서 에이전트가 답함
```

- 재개는 승인함 만료 처리처럼 **사람 요청 없이** `input.respond` 처리기를 부른다(실행자 = 채팅한 사람). 재개 값 검사에
  `workflow_wait` 형식을 더해, 그 대기의 워크플로 실행 ID와 실제로 끝난 실행의 결과만 받는다(다른 사람이 임의 결과로 재개하지 못하게:
  사용자 `input.respond`로 온 `workflow_wait` 응답은 거부).
- 멱등: 같은 워크플로 실행에 재개는 한 번(`claim_resume`). 작업이 두 번 돌아도 두 번째는 아무것도 하지 않는다.
- 워크플로가 즉시 실패(입력 오류, 에이전트 바뀜 등)하면 멈추지 않고 바로 오류를 도구 결과로 돌려준다.

### 3.3 취소와 끝맺음

- 멈춘 채팅을 취소하거나 그 대기를 버리면(새 메시지로 넘어감 등) 워크플로 실행을 취소한다(`cancel_run`, 대기 승인 요청도 취소).
- 워크플로를 실행 상세에서 취소하면 채팅은 `{status: "canceled"}` 결과로 이어진다.
- 워크플로 안의 승인·결과 불명 확인은 지금처럼 승인함에 들어가고, 채팅 카드에도 같은 요청이 보인다(결정은 compare-and-set 한 번).
- 따로 시간 한도는 두지 않는다(ADR-026 6절: 기다리는 곳마다 기한이 있음).

### 3.4 실행 기록·감사·사용량·기억

- `workflow_runs.parent_conversation_run_id`(NULL 허용, 마이그레이션). 실행 목록·상세에 "채팅에서 시작" 표시와 대화 링크.
- 감사: `workflow.run_start` 메타데이터에 `parent_conversation_run_id`, `started_from="chat_tool"`. 새 감사 동작 없음.
- 사용량: 단계는 지금처럼 `WORKFLOW`로 실행자에게. 채팅 실행 화면에는 "이 호출로 쓴 워크플로 사용량"을 합쳐 보여 준다(조회 시 합산,
  T8).
- 기억: 단계는 지금처럼 `run_path="workflow"`(Q4). 채팅 기억 경로는 바뀌지 않는다.

### 3.5 화면

| 영역 | 설계 |
|---|---|
| 에이전트 설정 | 도구·스킬 다이얼로그에 "워크플로" 종류: 내가 실행할 수 있는 게시된 워크플로 목록(이름, 입력 요약, 게시 버전). 끊긴 연결은 사유와 함께 |
| 채팅 카드 | `workflow_<id>` 도구 호출을 워크플로 카드로: 이름, 상태 칩(실행 중·승인 대기·결과 불명·완료·실패·취소), "실행 상세 열기", 승인 대기면 그 승인 카드(채팅 안에서 결정), 끝나면 출력 요약 |
| 실행 상세 | "채팅에서 시작" 배지와 대화로 가는 링크 |

## 4. 결정 질문 (추천안, 사용자 확인 전)

| 번호 | 결정할 내용 | 선택지 | 추천 |
|---|---|---|---|
| T1 | 채팅이 워크플로를 어떻게 기다리나 | A) 멈췄다가 끝나면 자동으로 이어 감 B) 일정 시간(예: 2분)만 기다리고, 넘으면 "실행 중, 결과는 실행 상세에서"로 끝냄 | **A**. 기획 3.9 결정(표준 인터럽트로 멈추고 결과로 재개)과 같고, 승인으로 며칠 걸려도 결과가 대화로 돌아온다. B는 쉬우나 결과가 대화에 안 돌아와 "도구"라고 하기 어렵다 |
| T2 | 멈춘 동안 같은 대화에 새 메시지 | 막음 / 허용하면 대기를 버리고 워크플로 취소 / 허용하고 결과가 나중에 끼어듦 | **승인 대기와 같은 규칙**(기존 인터럽트 동작 그대로). 결과가 나중에 끼어드는 방식은 대화 순서가 꼬인다 |
| T3 | 어느 버전을 부르나 | 부르는 시점의 게시 버전 / 연결할 때 버전 고정 | **부르는 시점의 게시 버전**. 워크플로를 고쳐 다시 게시하면 바로 반영된다. 인자 스키마도 그 버전에서 만든다 |
| T4 | 워크플로 안에서 다시 워크플로 부르기 | 허용(깊이 제한) / 막음 | **막음**. 워크플로 단계·하위 에이전트 실행에는 워크플로 도구를 붙이지 않는다. 서로 부르는 순환을 원천 차단 |
| T5 | 한 번에 여러 워크플로 도구 호출 | 허용 / 한 번에 하나 | **한 번에 하나**(같은 턴에 둘째 호출은 "앞 워크플로가 끝난 뒤 다시"를 결과로). 재개 값을 하나로 유지 |
| T6 | 누가 부를 수 있나 | 워크플로 소유자만 / 에이전트를 공유받은 사람도 | **소유자만(1차)**. 워크플로가 아직 소유자 전용(Q5)이라, 공유받은 사람의 채팅에는 도구가 붙지 않는다. 공유는 OpenFGA `workflow` 타입과 함께 |
| T7 | 예약·Agent API에서 부르기 | 함께 / 나중 | **나중**(확장 2). 무인 실행의 대기·정리 경로가 따로 있어 같이 열면 범위가 두 배가 된다 |
| T8 | 사용량 표시 | 단계별 그대로 / 채팅 실행에 합쳐 보여 줌 | **기록은 단계별 그대로, 채팅 화면에서만 합쳐 보여 줌**. 사용량 귀속 규칙(`attribution`)을 바꾸지 않는다 |

## 6. 위험

| 위험 | 대응 |
|---|---|
| 사람 없는 재개가 엉뚱한 실행을 재개 | 대기 인터럽트에 워크플로 실행 ID를 넣고, 재개 작업은 그 실행이 끝났고 부모가 아직 그 대기로 멈춰 있을 때만 재개 |
| 재개가 job worker와 API 프로세스 사이에서 길을 잃음 | 재개 처리기는 지금 채팅 재개와 같은 실행 접수 경로를 쓴다. T-b 첫 작업으로 job worker에서 `input.respond` 경로를 부를 수 있는지 실증 |
| 도구 인자 스키마가 바뀌는 사이 호출 | 부르는 시점 버전으로 검사하고, 입력 오류는 즉시 도구 결과로 |
| 순환 호출 | T4: 워크플로·하위 에이전트 실행에는 도구를 붙이지 않음 + 시험 |
