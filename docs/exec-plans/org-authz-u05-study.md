## 1. 목표와 성공 기준

### 1.1 확인할 질문

1. 소유자가 에이전트를 그룹에 원하는 단계(실행·보기·편집·관리)로 공유할 수 있는가. 단계 이름과 위임
   계정 경고를 이해하는가 (S16).
2. 공유받은 사람이 시작 전 점검에서 무엇이 막혔는지 알아보고, 스스로 연결해 대화를 시작할 수 있는가
   (S21, S23). 대화 중 인증 카드를 보고 이어서 실행할 수 있는가 (S22).
3. 조직 관리자가 구성원을 제거하면서 소유 자원을 다른 사람에게 넘길 수 있는가. 2단계의 회수·정지
   영향을 이해하는가 (S15, S17).
4. 권한이 없는 자원 앞에서 권한을 요청할 수 있는가 (S02 권한 안내, S18 요청 대화상자).
5. 회사 관리자가 회사 카탈로그에서 항목을 끄고, 그 결과가 조직 카탈로그에 어떻게 보이는지 이해하는가
   (S07 회사 카탈로그, 조직 카탈로그 정책).

### 1.2 성공 기준

| 기준 | 값 | 출처 |
|------|----|------|
| 전체 과업 성공률 | **80% 이상** (도움 없이 성공한 시도 / 전체 시도) | 1.3 |
| 막힌 지점 | 실패·도움·시간 초과가 난 지점마다 수정안을 정하고, 수정이 반영될 때까지 1.3 미충족 | 1.3, 17장 U-05 |
| 참가자 | 사내 사용자 3~5명 | 17장 U-05 |

과업별 참고 지표(게이트 아님): 과업별 성공률, 목표 시간 안 완료율, SEQ 중앙값, UMUX-Lite 평균.
참가자가 3~5명뿐이라 비율은 반드시 원시 건수(예: 4/5)와 함께 적습니다.

## 2. 참가자 모집

### 2.1 인원과 역할 구성

| 역할 | 인원 | 시험 중 로그인할 계정(시드 인물) | 맡는 과업 |
|------|------|----------------------------------|-----------|
| 조직 관리자(회사 관리자 겸) | 1~2 | 김지원 `playwright-e2e@moldy.dev` | T1, T3, T5 (+ T4 승인 선택) |

`correct horse battery staple 42`입니다(시험용 일회성 스택의 고정값, 2.3절).

### 2.2 선별 기준

포함:

- 사내에서 Moldy 또는 비슷한 사내 도구(에이전트 빌더, 공유 드라이브, 사내 권한 신청 시스템)를 지난
  3개월 안에 써 본 사람.
- 관리자 역할 지원자는 실제로 팀·조직의 계정이나 권한을 관리해 본 경험이 있는 사람.
- 빌더 역할 지원자는 에이전트·자동화를 직접 만들어 다른 사람과 나눠 써 본 사람.

제외:

- org-authz 기획·구현·리뷰에 참여한 사람, 13.14 시안이나 캡처 투어를 본 사람.
- 같은 팀에서 이미 다른 참가자의 세션을 참관한 사람.

선별 질문(메신저나 설문으로 사전 확인):

1. 지난 3개월 동안 Moldy를 몇 번 썼나요? (안 씀 / 1~5회 / 매주)
2. 에이전트나 자동화를 직접 만들어 다른 사람과 공유한 적이 있나요?
3. 팀원 계정 추가·삭제, 권한 부여를 직접 해 본 적이 있나요?
4. 조직·권한 기능 개발이나 리뷰에 참여했나요? (예 → 제외)
5. 60분 화상 또는 대면 세션이 가능한 시간대

질문 2·3의 답으로 역할을 배정합니다. 둘 다 "예"면 관리자, 2만 "예"면 빌더, 둘 다 "아니요"면
구성원입니다.

## 3. 환경 준비

### 3.1 구성 개요

시험 스택은 기존 일회성(throwaway) 스택 방식에 캡처 투어 시드를 얹어 만듭니다.

1. **기본 DB 만들기**: 일회성 PostgreSQL에 마이그레이션을 적용하고, 캡처 투어
   (`frontend/e2e/captures/captures-org-authz.spec.ts`)를 한 번 돌려 시드 helper
   (`frontend/e2e/helpers/org-authz-seed.ts`, `org-authz-seed-resources.ts`)로 실제 데이터를 넣습니다.
   투어가 끝나면 Playwright가 띄운 서버는 내려가지만 DB 내용은 남습니다.
2. **추가 준비 데이터**: legacy 모드로 시험 서버를 띄워 과업에 필요한 데이터 몇 개를 화면에서 더
   만듭니다(3.4절). 그 뒤 서버를 내리고 이 DB를 **템플릿**으로 둡니다.
3. **세션마다 복제**: 참가자마다 템플릿을 복제한 새 DB와 새 OpenFGA(메모리 저장)로
   `AUTHZ_MODE=enforce` 스택을 띄웁니다. 앞 참가자의 공유·제거·카탈로그 변경이 다음 참가자에게 남지
   않습니다.

템플릿은 OpenFGA bootstrap 전 상태로 둡니다. bootstrap이 `authz_model_versions`에 store ID를 기록하므로,
bootstrap한 DB를 복제하면 새 OpenFGA에서 없는 store를 가리키게 됩니다.

> **주의**: 아래 명령은 저장소의 스크립트·설정에서 옮겨 적은 것이고, 이 키트를 쓰는 시점에는 한 번도
> 끝까지 실행해 보지 않았습니다. 본 시험 전에 진행자 한 명이 5절의 파일럿과 함께 리허설합니다. 특히
> enforce 스택의 bootstrap과 시드 계정 로그인은 리허설에서 확인합니다.

### 3.2 공통 환경 변수

저장소 루트에서 한 셸을 열고 아래 값을 세션 내내 씁니다. `backend/.env`(main 체크아웃의 실제 설정으로
연결된 경우가 있음)를 읽지 않도록 `MOLDY_DISABLE_ENV_FILE=true`를 반드시 켭니다. 암호화 키와 JWT
비밀은 시험 전용으로 새로 만들고, 시드 실행과 시험 서버가 **같은 값**을 써야 시드한 자격증명이 풀립니다.

```bash
export REPO="$PWD"                                   # 저장소(또는 worktree) 루트
export PY="$REPO/backend/.venv/bin/python"           # worktree면 main 체크아웃의 backend/.venv 경로
export U05_PG_PORT=5435
export U05_BASE_DB=moldy_e2e_scripted_u05            # E2E 설정이 moldy_e2e_scripted* 이름만 허용
export ENCRYPTION_KEYS="$(openssl rand -hex 32)"
export JWT_SECRET="$("$PY" -c 'import secrets; print(secrets.token_urlsafe(48))')"
export MOLDY_DISABLE_ENV_FILE=true PYTHON_DOTENV_DISABLED=1
export RATE_LIMIT_ENABLED=false
# 두 값을 파일로 남겨 다음 셸에서 다시 export한다(시험 종료 후 파일 삭제).
printf 'export ENCRYPTION_KEYS=%s\nexport JWT_SECRET=%s\n' "$ENCRYPTION_KEYS" "$JWT_SECRET" \
  > "${TMPDIR:-/tmp}/u05-secrets.sh"
```

### 3.3 기본 DB와 캡처 투어 시드

```bash
# 1) 일회성 PostgreSQL (다른 E2E·캡처 스택과 겹치지 않는 5435)
docker run -d --name moldy-u05-pg -p 127.0.0.1:${U05_PG_PORT}:5432 \
  -e POSTGRES_DB=${U05_BASE_DB} -e POSTGRES_USER=moldy -e POSTGRES_PASSWORD=moldy \
  postgres:16-alpine

export DATABASE_URL="postgresql+asyncpg://moldy:moldy@localhost:${U05_PG_PORT}/${U05_BASE_DB}"
export DATABASE_URL_SYNC="postgresql://moldy:moldy@localhost:${U05_PG_PORT}/${U05_BASE_DB}"

# 2) 마이그레이션 — 이 일회성 DB에만 실행
(cd backend && "$PY" -m alembic upgrade head)

# 3) 캡처 투어로 시드 (Playwright가 backend 8101 / frontend 3100을 직접 띄우고 끝나면 내림)
cd frontend
E2E_CAPTURE_TOUR=1 E2E_SEED_USER_ENABLED=true E2E_TEST_HELPERS_ENABLED=true \
MOLDY_GATE_PYTHON="$PY" \
pnpm exec playwright test e2e/captures/captures-org-authz.spec.ts --project=scripted-capture
cd ..
```

- 투어는 legacy 모드로 돕니다(Playwright 설정이 넘기는 환경 변수 목록에 `AUTHZ_MODE`가 없음). 시드는
  DB 행(`resource_grants`, 조직·그룹 테이블)으로 남고, 3.5절의 bootstrap이 이를 OpenFGA 튜플로
  옮깁니다.
- `DEPLOYMENT_MODE`가 기본값 `single_tenant`이므로 플랫폼 회사 3곳(한빛물산 등) 생성 요청은 실패
  로그만 남깁니다. 이 시험은 S03/S04를 다루지 않으므로 무시합니다.
- 투어 로그 마지막의 `failed N: [...]`가 0이 아니어도 시드 자체는 앞부분 `seed()`에서 끝납니다. 아래
  시드 목록이 화면에 있는지만 확인합니다.
- 캡처 PNG는 `output/captures/org-authz/`에 생깁니다. 참가자에게 보여 주지 않습니다.

투어가 남기는 시드 데이터(헬퍼 코드 기준):

|------|------|

### 3.4 추가 준비 데이터 (템플릿에 한 번)

legacy 모드로 시험 서버를 띄우고(3.6절 명령에서 `AUTHZ_MODE=legacy`, OpenFGA 변수 없이) 화면에서

| ID | 로그인 | 만들 것 | 쓰는 과업 |
|----|--------|---------|-----------|

| D2 | 이하은 | 에이전트 **회의록 요약 도우미**(scripted 모델, 시스템 프롬프트 한 줄) | T1(빌더) |


D1의 스킬 ID는 T4 관찰용으로 적어 둡니다(주소창 `/skills/<id>` 또는 `GET /api/skills`).

### 3.5 세션마다 enforce 스택 띄우기

참가자마다 `P=p1`, `p2`… 로 바꿔 실행합니다.

```bash
source "${TMPDIR:-/tmp}/u05-secrets.sh"
export P=p1
export U05_DB=${U05_BASE_DB}_${P}
docker exec moldy-u05-pg psql -U moldy -d postgres -c \
  "CREATE DATABASE ${U05_DB} TEMPLATE ${U05_BASE_DB};"

export DATABASE_URL="postgresql+asyncpg://moldy:moldy@localhost:${U05_PG_PORT}/${U05_DB}"
export DATABASE_URL_SYNC="postgresql://moldy:moldy@localhost:${U05_PG_PORT}/${U05_DB}"
export MIGRATION_DATABASE_URL="$DATABASE_URL"

# 새 OpenFGA (메모리 저장, 이 세션 전용, 루프백에만 노출)
export OPENFGA_API_TOKEN="$("$PY" -c 'import secrets; print(secrets.token_urlsafe(32))')"
docker rm -f moldy-u05-fga 2>/dev/null
docker run -d --name moldy-u05-fga -p 127.0.0.1:18080:8080 openfga/openfga:v1.22.0 run \
  --authn-method=preshared --authn-preshared-keys="$OPENFGA_API_TOKEN" --playground-enabled=false
export OPENFGA_API_URL=http://127.0.0.1:18080

# bootstrap: 모델 배포 + Postgres 기준 기대 튜플 전부 기록. 출력 JSON의 store/model ID를 고정
(cd backend && AUTHZ_MODE=legacy "$PY" -m app.authz.cli bootstrap | tee "${TMPDIR:-/tmp}/u05-${P}-bootstrap.json")
export OPENFGA_STORE_ID=<출력 model.store_id>
export OPENFGA_MODEL_ID=<출력 model.model_id>

# 카탈로그 fanout 백필 후 차이 확인 (종료 코드 0이어야 함)
ADMIN_ID=$(docker exec moldy-u05-pg psql -U moldy -d ${U05_DB} -tAc \
  "select id from users where email='playwright-e2e@moldy.dev'")
(cd backend && "$PY" -m app.authz.cli catalog-fanout --actor "$ADMIN_ID")
(cd backend && "$PY" -m app.authz.cli reconcile --dry-run --json)
```

### 3.6 시험 서버 실행

```bash
export AUTHZ_MODE=enforce AUTHZ_ENFORCE_TYPES=     # 빈 값 = 전 유형 강제
```

### 3.7 enforce 데이터가 필요한 화면

| 화면 | legacy에서 | 시험에서 필요한 것 |
|------|------------|--------------------|
| S02 권한 안내, S18 권한 요청 (T4) | 소유자 판정만 해서 `403 permission_required`가 나오지 않음 | **enforce 필수**. D1 스킬을 사용 단계로 받은 사람이 설정을 열 때 403 |
| S18 요청함 승인 (T4 선택) | 요청이 생기지 않음 | enforce + T4에서 만든 요청 |
| S15 "지금 바로 이전" (T3) | 설계상 숨김(legacy 관리자 `can_transfer_now=false`) | enforce에서만 나타남. 관찰 항목 |
| S20 실행자 화면, 보기 전용 설정 | `my_permissions`가 소유자 기준 | enforce. T1 결과를 받은 사람 쪽 확인용(진행자 확인) |
| S21 점검 패널·카드 배지 (T2) | 투어·E2E 모두 route 재생 | enforce + 사용자마다 연결 MCP가 필수로 붙은 에이전트. 시드 helper에는 없음(3.8절) |
| S22 인증 카드 (T6) | route 재생 | 실제 만료를 만들려면 enforce + MCP 401 고정 장치가 필요한데 아직 없음(3.8절) |
| 카탈로그 끄기의 실행 영향 (T5) | 정책은 저장만 되고 튜플로 투영되지 않음 | enforce. 화면 과업 자체는 legacy로도 가능 |

T1(S16 공유), T3(S15 제거), T5(S07 카탈로그) 화면은 legacy에서도 동작하지만, 시험은 한 스택에서 모두
진행하도록 enforce로 통일합니다.

### 3.8 S21·S22 대체 경로 (클릭 가능한 재생 화면)

16.5의 enforce 역할 고정 장치와 사용자마다 연결 MCP 고정 장치가 아직 없어서, S21·S22는 기존 opt-in
E2E 스펙이 `page.route`로 재생하는 상태를 참가자가 직접 누르게 합니다. 17장 U-05가 허용하는 "클릭
가능한 시안"에 해당합니다.

```bash
cd frontend
# T2: 점검 패널 → 연결하기 → 내 Slack 연결 → 확인 → 대화 시작
E2E_ORG_AUTHZ=1 E2E_SEED_USER_ENABLED=true E2E_TEST_HELPERS_ENABLED=true \
MOLDY_GATE_PYTHON="$PY" PWDEBUG=1 \
pnpm exec playwright test e2e/readiness-connect-start.spec.ts --project=scripted-full \
  --headed -g "connects my account from the check panel"

# T6: 대화 중 인증 카드 → 연결하기 → 이어서 실행
E2E_ORG_AUTHZ=1 E2E_SEED_USER_ENABLED=true E2E_TEST_HELPERS_ENABLED=true \
MOLDY_GATE_PYTHON="$PY" PWDEBUG=1 \
pnpm exec playwright test e2e/readiness-auth-card-connect.spec.ts --project=scripted-full --headed
```

- 이 명령은 3.3절처럼 자체 backend(8101)·frontend(3100)를 띄우므로 3.6절 시험 서버와 같은 DB를 쓰지
  않게 `DATABASE_URL`을 `moldy_e2e_scripted_u05_replay` 같은 별도 DB(마이그레이션 적용)로 바꿔 둡니다.
- Playwright Inspector에서 진행자가 `page.goto`까지 한 단계씩 진행(Step over)해 첫 화면(“필수 항목
  1개 연결이 필요해요” 카드, 또는 인증 카드)이 보이면 멈춘 상태로 브라우저를 참가자에게 넘깁니다.
  Inspector가 멈춰 있어도 route 재생은 계속 동작하므로 참가자가 직접 누를 수 있습니다. 참가자가 끝나면
  진행자가 창을 닫습니다(스펙의 이후 자동 클릭은 실행하지 않음).
- 재생 화면은 시드 관리자(김지원) 세션으로 열립니다. 참가자에게 "공유받은 사람 입장"이라고 미리
  말해 둡니다. 이 한계는 결과 기록에 함께 적습니다.
- Inspector 멈춤 상태에서 참가자 조작이 가능한지는 파일럿에서 먼저 확인합니다. 안 되면 진행자가
  캡처 PNG(`36-g04-readiness-collapsed-card.png` ~ `39-g05-auth-required-card.png`)를 순서대로 보여
  주는 종이 시안 방식으로 바꾸고, 그 과업은 성공률 계산에서 "시안 과업"으로 따로 표시합니다.

### 4.3 과업 진행 규칙

- 과업 카드를 소리 내어 읽어 주고 출력본도 건넵니다. 카드에는 목표만 쓰고 화면 이름·버튼 이름은 쓰지
  않습니다.
- 시간은 카드를 다 읽은 순간부터 잽니다. 참가자가 "다 됐어요"라고 하거나 포기하면 멈춥니다.
- 목표 시간의 2배가 지나면 "여기까지 하고 다음으로 가 볼게요"라고 말하고 실패로 기록합니다.
- 도움(힌트)은 참가자가 2분 이상 진전이 없을 때 한 번만, 아래 순서로 줍니다. 도움을 받으면 그 시도는
  성공률 계산에서 실패입니다.
  1. "지금 무엇을 찾고 계세요?"
  2. "그 일을 하려면 어느 화면부터 보시겠어요?"
  3. (마지막) 해당 화면으로 이동만 시켜 줌. 버튼은 알려 주지 않음.
- 과업이 끝날 때마다 SEQ(6.1절)를 묻습니다.

### 4.4 중립 질문 예시

쓸 말:

- "지금 무엇을 보고 계세요?" / "어떤 생각이 드세요?"
- "그걸 누르면 어떻게 될 거라고 예상하세요?"
- "방금 결과가 예상과 같았나요?"
- "계속 말씀해 주세요."
- (침묵 15초 이상) "지금 어떤 고민 중이세요?"

쓰지 않을 말: "그 버튼 맞아요", "잘하셨어요", "거의 다 왔어요", "보기 단계를 고르세요", 화면 용어
("공유 대화상자", "점검 패널", "마법사")를 먼저 꺼내는 말. 참가자가 질문하면 "실제로 혼자 하신다면
어떻게 하시겠어요?"로 되돌립니다.

## 5. 파일럿

본 시험 전에 org-authz 작업에 참여하지 않은 사내 인원 1명과 파일럿을 1회 합니다. 확인할 것:

- 3.3~3.6 명령이 끝까지 실행되는지, enforce 스택에서 시드 계정 로그인과 T4의 403이 나오는지.
- 3.8 재생 화면에서 참가자가 Inspector 멈춤 상태로 조작할 수 있는지.
- 과업 카드 문구가 정답을 흘리지 않는지, 목표 시간이 현실적인지.

파일럿 결과는 성공률에 넣지 않습니다. 과업·문구를 바꿨다면 이 문서를 고친 뒤 본 시험을 시작합니다.

### T3. 구성원 제거하면서 소유권 이전 (S15, S17)

| 항목 | 내용 |

## 7. 사후 설문

### 7.1 과업마다: SEQ

> "방금 과업은 전반적으로 얼마나 어렵거나 쉬웠나요?"
> 1 (매우 어려움) – 2 – 3 – 4 – 5 – 6 – 7 (매우 쉬움)

5 미만이면 "어떤 점 때문에 그렇게 고르셨나요?"를 한 번 묻고 기록합니다.

### 7.2 마지막: UMUX-Lite

과업 수가 적고 세션이 짧아 SUS(10문항) 대신 UMUX-Lite(2문항)를 씁니다. 7점 척도, 1 = 전혀 그렇지
않다, 7 = 매우 그렇다.

1. 이 화면들의 기능은 내가 필요로 하는 일을 해 준다.
2. 이 화면들은 쓰기 쉽다.

점수 = ((문항1 − 1) + (문항2 − 1)) / 12 × 100. SUS와 비교하려면 SUS 환산값 = 0.65 × UMUX-Lite + 22.9
(Lewis 외, 2013)를 함께 적습니다. 참가자 3~5명의 평균은 참고값이며 게이트가 아닙니다.

### 8.3 성공률 계산

- **전체 성공률** = (결과가 S인 행 수) / (전체 시도 행 수). A와 F는 모두 실패로 셉니다. 진행 장애(스택
  오류, 재생 화면 멈춤 등 화면과 무관한 원인)로 중단한 행은 분모에서 빼고 비고에 이유를 적습니다.
- 판정: 전체 성공률 ≥ 80%면 1.3의 성공률 조건 충족. 예) 4명 × 평균 3.5과업 = 14시도 중 S 12건 →
  85.7% 충족, S 11건 → 78.6% 미충족.
- **과업별 성공률**도 함께 냅니다(예: T3 2/3). 전체가 80%를 넘어도 80% 미만인 과업, F 또는 A가 하나라도
  나온 지점은 모두 "막힌 지점"으로 8.4절에 올립니다. 1.3은 막힌 지점의 수정 반영까지 요구합니다.
- "방식"이 재생·시안인 과업(T2, T6)은 같은 식으로 셈하되 결과 보고에 "재생 화면 기준"이라고
  밝힙니다. 실제 enforce 고정 장치가 생기면 해당 과업만 다시 시험할지 결정합니다.

## 9. 결과 반영

1. 세션이 모두 끝나면 진행자와 기록자가 함께 8.1~8.4를 채우고 성공률을 계산합니다.
2. 결과와 결정은 [실행 기록](org-authz-progress.md)에 남깁니다. 실행 기록이 현재 결정을 담는
   문서이므로, 17장 U-05 행이 말하는 "13.14 반영"은 실행 기록의 다음 두 곳으로 대신합니다.
   - P8 checklist의 U-05 행: 시험일, 참가자 수와 역할 구성, 전체·과업별 성공률(원시 건수), UMUX-Lite
     평균, 발견 목록 요약, 1.3 충족 여부.
   - "Decision changes and clarifications": 13.14 시안과 달라지는 화면 결정(문구·배치·단계 이름 등)을
     날짜와 함께 한 줄씩.
3. 기획서 HTML(13.14)을 고칠지는 별도로 정합니다. 고친다면 `scripts/check_plan_history.py`가 요구하는
   변경 이력 규칙을 따릅니다.
4. 각 발견은 아래 후속 작업에 배정하고, 실행 기록의 해당 U 행에 "U-05 후속" 항목으로 추가합니다.
   수정이 커밋되면 발견 목록 상태를 "반영"으로 바꿉니다. 높음·중간 발견이 모두 반영되어야 1.3의
   "막힌 지점의 수정이 반영됩니다"를 충족한 것으로 봅니다.
